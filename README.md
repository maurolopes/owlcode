# owlcode

owlcode is an agent loop for coding agents. The name reads as "I'll code": the owl works at night while the owner sleeps.
A person writes issues in Linear, agents implement them on a Mac, a reviewer agent reviews them, and GitHub merges
approved pull requests. Products keep a pinned copy of the loop's files, and a check refuses hand edits.

## How a change flows

1. A person writes an issue in Linear and puts it in Todo.
2. Each round, a background orchestrator on a Mac reads Linear and starts a coding agent for each Todo issue, within a
   limit on how many run at the same time.
3. An inference profile picks the harness, models, and effort level, using stronger settings for labels like
   "intricate".
4. Each session opens in herdr or Paseo, where a person can watch and steer it, including from a phone.
5. The agent works in its own git worktree and branch, runs project checks, and opens a pull request.
6. To ask the owner a question, the agent comments on the Linear issue, moves it to a waiting state, and stops.
7. A reviewer agent on GitHub Actions checks a fixed merge bar: wrong behaviour, data loss, a broken security or privacy
   property, a broken documented promise, or failed checks. It requests small fixes in the same files once, makes
   follow-up issues for other findings, and sends the issue to the owner after at most three rounds.
8. Once the reviewer approves and required checks pass, GitHub merges the pull request automatically. A change to the
   files that check the agents' work (the workflows and scripts of `.github/`, the hooks, the guards, the reviewer's
   brief: `.github/CODEOWNERS`) waits for the owner's review and merge.

## What you need

* A Mac (macOS) for the orchestrator and agents, with Python 3.11 or newer from python.org for the service.
* A Linear workspace.
* GitHub repositories with branch rulesets.
* Two GitHub Apps: one for the implementer and one for the reviewer.
* A coding agent harness: Claude Code on a Claude subscription, or pi on Ollama Cloud, a ChatGPT plan or LithosAI (the
  inference profiles of `orchestrator/model-catalog.json`).
* A session host: herdr or Paseo.
* `mise` and `uv`.

## Getting started

Read the "Setting up a product" section in `agents/README.md` before adding owlcode to a repository. A product takes a
pinned copy of the loop's files, and its `mise run loop:bump` moves that pin to a newer owlcode commit. On the Mac,
`owlcode install` installs the orchestrator as a service (the section "The `owlcode` command" below). The decisions and
their reasons are in `DECISIONS.md`, and the rules for a change here are in `AGENTS.md`.

## What this is not

* Not a supported product: this is a personal project developed in public under the MIT license. It gives no support,
  takes no outside issues or pull requests, and has no releases, no changelog, and no package.
* Not unrestricted access: agents run as a separate standard macOS user with its own keychain. They cannot edit the
  main checkout, push to main, change repository rules, or change the workflow files that check their work.
* Not a chat: an autonomous run never waits for an answer in its session. Its questions go to the Linear issue.

# Reference

## How a product uses the loop

A product keeps a copy of the files that `.workflow/loop-files.txt` lists, at the paths where the harnesses and the
workflows read them, at one commit of this repository that it records. The product's bump task copies the files of a
new commit and prints the diff since the old one, so the owner reads each change before it runs with the product's
keys. That task and the check are the loop's own script, `.workflow/loop_sync.py` (a listed file): the product's
`mise.toml` calls it, `loop:bump` with `/usr/bin/python3 -I .workflow/loop_sync.py bump "$@"` and `loop:check` with
`/usr/bin/python3 -I .workflow/loop_sync.py check`, and the product keeps its pin in `.workflow/loop.toml`
(`repository = "OWNER/NAME"`, `commit = "FULL_SHA"`). One command makes a bump: `mise run loop:bump [REF]` (REF: a ref of
this repository's main, default `main`), run in the product's main checkout, pulls main, makes the worktree
`.claude/worktrees/loop-bump-SHORT`, copies the files, writes the pin, commits, pushes and opens the pull request, then
prints its URL. A pin that stands at REF's commit prints `the pin stands at SHORT: nothing to do`. Such a pure bump needs
no issue: its branch is `loop-bump-SHORT` (SHORT: the first 12 hex digits of the new pin), its diff changes only the pin and
the listed files, and the owner reads it and merges it. A bump that also needs a product change is not pure: it needs an issue
and a keyed branch (the review fails the check `verdict` for a `loop-bump-...` branch that changes a product file). A check in the product's gates refuses a copy that differs from this repository at the recorded commit: a fix to
the loop is a pull request here, then a bump (DECISIONS.md "A product takes the loop's files at a pinned commit").

The product holds what the loop leaves to it: its AGENTS.md (its gates, its teams in "The teams", its rules), its
`.github/CODEOWNERS` and its gates workflow. The orchestrator's config with its `[[product]]` tables lives on the Mac
(`/usr/local/etc/orchestrator.toml`, from this repository's `orchestrator/orchestrator.example.toml`), not in the
product. agents/README.md "Setting up a product" has the steps.

The Mac's tools are not in the copy: `orchestrator/`, `.workflow/agent_user.py`, `.workflow/approved_run.py`,
`.workflow/model-catalog.json` and their tests. The service runs the installed copy, the agents' home copy of
`agent_user.py` comes from the checkout that runs `admin`, and the owner runs each `owlcode` command (`bin/owlcode`) from this repository's checkout, one machine for all products. A product's `mise.toml` needs none of
those commands. A product's next bump prints these files as `kept`: the product removes them, and its tasks, in its own pull
request.

## The `owlcode` command (on your Mac)

The commands you type for the orchestrator and the agents' user are one program, `bin/owlcode`. Put the checkout's `bin` on
your PATH once: `export PATH="$HOME/dev/owlcode/bin:$PATH"` in `~/.zshrc`. `owlcode` with no command, or `owlcode help`, prints the list:

```
owlcode install                                     install the orchestrator as a service: the commits, a dry round of each side by side, then a yes (sudo)
owlcode check                                       check the service: the keys, Linear and GitHub, a recent round, long sessions, an old install, and the install's own properties (sudo); exit 1 on a FAIL
owlcode restart                                     restart the service after an edit of its config: one dry round on the config first, then the restart, then the check (sudo)
owlcode set KEY=VALUE...                            change top-level keys of the config (owlcode set inference_profile=claude): the diff, the preflight and one dry round on a copy, then the write and the restart (sudo)
owlcode profile [NAME]                              list the inference profiles and switch to the one you pick by number or by name: the same checks and restart as set (sudo)
owlcode pause                                       hold the new starts and fix escalations until owlcode resume; wakes, closes and the queue go on (sudo)
owlcode resume                                      end the pause: the service starts again in its next round (sudo)
owlcode unlock                                      unlock the agents' keychain in the service's own session, once after each restart of the Mac (sudo, then the keychain's password)
owlcode watch [--once]                              draw the orchestrator's plan of every team in place, as [service] user, until Ctrl-C; --once prints it one time (sudo)
owlcode models                                      show the inference catalog's valid combinations and token prices
owlcode models-check                                compare catalog IDs with the providers' model lists, as the agents' user
owlcode admin [--project TEAM|--orchestrator NAME]  make the agents' group, user and home, and copy agent_user.py there; the user is [service] user of the config, or with --project the agent_user of that team's table, with its clone and Paseo port, or with --orchestrator NAME the orchestrator's own user, with its keychain only: no session runs there (sudo)
```

Each command runs the script that its `mise` task ran before, through `.workflow/approved_run.py` (`models-check` runs as the
agents' user and skips the launcher). `owlcode admin` takes the agents' user from `[service] user` of
`/usr/local/etc/orchestrator.toml` and stops when the file has none: it never makes a user named after the checkout.
`owlcode admin --project TEAM` takes the user from the `agent_user` of that team's table instead, with the team's
repository and `paseo_port`, and refuses a table with no `agent_user` or with `[service] user` there (agents/README.md "Setting up a product", step 7).
`owlcode admin --orchestrator NAME` makes the orchestrator's own user NAME, where no session runs (the row "The
orchestrator's own user" below). An unknown command prints the list and exits 2.

## The agents' macOS user (on your Mac)

The coding agents run as a Standard user in the group `agents`, with the implementer app's key and no way to a
product's server (`.workflow/agent_user.py`). The script holds no name: as root or as you, it takes the user's name from
your checkout's `origin` (the repository's name); in the agents' account, the login name of the account (never `$USER`,
which `su` keeps); `AGENT_USER=NAME` overrides both (with sudo: `sudo AGENT_USER=NAME ...`). The rows below call that
user `agents`. An issue with the Area `workflow` runs there too: the app cannot push a file under `.github/workflows/`,
so the run writes that change as a patch on its pull request, and the owner's label `apply-workflow-patch` applies it
(agents/implementer.md step 6). Never run the agents' checkout from your account: its hooks and scripts would run as
you.


Two kinds of user (the owner's call of 2026-11-26, design b2):

- **A project's agents' user** (`owlcode admin --project TEAM`, or the one shared user of an older setup, `owlcode
  admin`): the sessions run there. It holds the project's clone, its harnesses and their sessions, its own Paseo daemon
  with its own password and port, and its herdr machine. Its keychain holds the project's keys only: the implementer
  app's client ID and private key, the Claude token, the team's Linear key and the optional model keys.
- **The orchestrator's own user** (`owlcode admin --orchestrator NAME`; `[service] user = "NAME"` comes with the move,
  later): the service runs there, and no session ever does. It has no harness, no clone, no SSH login and no Paseo daemon. Its keychain
  (`agent.keychain-db`) holds the service's items only: each team's Linear key (`NAME-agent.linear-key`, and
  `NAME-agent.abc-linear-key` for a team whose `linear_key_env` is `ABC_LINEAR_API_KEY`), each daemon's password
  (the `paseo_password_item` of each product) and the orchestrator's app key (`app_key_item`). The service starts each session in its project's daemon (`paseo
  --host`). Switch `[service] user` to this user as the last step of the move: after each product has its own user, its `paseo_host` and its password item, and the orchestrator's keychain holds each team's Linear key and the orchestrator's app key. `owlcode check` knows this user by
  the full name `NAME orchestrator`, which only `admin --orchestrator` gives. No SSH login loads the service there after
  a restart, so for this user `owlcode install` and `owlcode restart` also write the boot job: a root LaunchDaemon
  `/Library/LaunchDaemons/LABEL.boot.plist` that runs once at each start of the Mac and loads the service into the
  user's domain `user/UID` (the row "Unlock the orchestrator's keychain after a restart").

### Check the orchestrator's run setup

To switch profiles, run `owlcode profile` (the row "Switch the inference profile"). To switch hosts, change only `session_host` (`owlcode set session_host=herdr`), with no wait for the agents that run: new sessions start on the new host, and the old host's sessions get their wakes and closes there until the last one closes. Use Paseo for pi. Claude Code supports herdr, Paseo and the detached process host. `owlcode install` removes the retired `run_command` line of an older config itself, and shows the edit with the new keys. The old copy can report that the key is missing in its side of the install comparison. The new copy must pass its preflight and dry round.

`owlcode install`, `owlcode restart` and `owlcode check` run the same setup preflight.
It checks the active profile's credential, as the service's user. When every product names its own `agent_user` and `paseo_host`, it skips that check, and `owlcode check` runs it as each product's user instead (orchestrator/README.md "Where each key_check runs"). For pi, it also checks each cell's `--model` and the local review model with
`pi --offline --no-approve --list-models`. It makes no model request. Claude Code gets the credential check only.
A failed preflight stops install or restart before it stops the service. It names the failure and the affected cell.
The install sets the staging folder's permissions without using your shell's umask. If the staged preflight or dry round
reports `Permission denied`, the install prints the staging folder's path and mode, or `mode unavailable`.
Before its dry round, restart sets the local review settings file and `inference-profile.json` to mode 644 so the agents' user can read it.

`owlcode check` also checks the running local Paseo daemon's profile (only when a product's sessions run there: a
product with no `paseo_host`) and compares a custom pi provider with the current
catalog. `agent_user.py paseo-daemon` records the profiles of the daemon that it starts: NAME, then each other profile that
NAME's cells run on. The preflight at `owlcode restart`, `owlcode set` and before a start reads
that record. A daemon that is stopped, or on other profiles, is a `WARN` (the service starts or switches it: the row
"The agents' Paseo daemon"); only a daemon whose status cannot be read, or that runs with no record of its own, fails. A line of
a mix reads `ok   Paseo daemon profiles: pi-lithosai, claude`. If a custom pi provider differs from the catalog, run `admin` to copy the current script and
catalog, then run `user` to update the provider. The harness continues to manage its built-in providers.

If a start fails before a session exists, the service halts new starts and fix escalations for all teams. It can still
wake existing sessions, close workspaces and update the queue. Look for `halted:` in the log, `--watch` and the pinned
queue, or for the assigned notice in Linear. A Paseo agent that stops in `error` within `claim_wait_seconds` of its
start, before its claim, is a setup failure too: the service halts the starts, archives that agent, and counts no try
for it. The service retries preflight every `halt_check_minutes`. If preflight passes but the same launch failure
recurs, the service keeps the halt and does not send the same notice again. For a halt from an agent in `error`, the
notice stays open until the restarted start claims, or its claim wait passes without an error. If the host cannot tell
whether a session exists, the service checks that launch before it retries preflight. A confirmed session
clears its halt in the same round. If the banner asks you to inspect the launch workspace, fix the host error that prevents
confirmation or cleanup. Preflight alone cannot do this. When the halt clears, starts resume and the notice closes.
To apply a config edit, use `owlcode restart` (a new `linear_key_env` needs `owlcode install`). To change a top-level key, use `owlcode set KEY=VALUE`.
Herdr confirms agent detection. The detached process host uses Claude Code's `init` event and saves its JSON output in
`log_dir`. Paseo retries cleanup by workspace ID and keeps workspaces that contain an agent. Use Paseo 0.17.1 or a
later version that includes `workspaceId` in its agent list. Without that field the service cannot confirm a workspace is empty.

### Update the inference catalog

In `[profiles.NAME]`, use catalog model IDs in all four cells and `review_model`. Keep any slash that is part of the
catalog ID (for example, `zai-org/GLM-5.3-Flash`). The launch commands add pi's provider prefix (for example,
`pi-lithosai/` or `openai-codex/`).

Edit [`orchestrator/model-catalog.json`](orchestrator/model-catalog.json) to add a model. Use the exact provider ID for each model or tier. Set its supported harnesses, effort mappings, context window and maximum output. Use `null` for an unverified limit and omit a harness from `efforts` until you verify its settings. Each price has a source URL and a date read, shared under `price_source` for models from the same provider page. Use the subscription entry instead of a token price for subscription models. The install adds any missing `provider` settings from the example. The orchestrator checks all profiles and their local review settings before it starts a round.
